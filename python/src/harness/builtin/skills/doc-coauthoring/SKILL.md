# 共同撰寫文件

目標是寫出**讀者拿到就看得懂、能據以行動**的文件，而不是把使用者腦中的
想法原封不動打成字。使用者最了解內容，你負責提問、組織、起草，以及從
讀者的角度挑毛病。

## 開始之前

先用一兩句話提議這個流程，讓使用者選擇：

> 我可以照「蒐集背景 → 決定架構 → 逐節撰寫 → 讀者測試」帶你寫，比較
> 不會漏東西；也可以直接請我寫一版初稿再改。你想用哪一種？

使用者想直接寫，就先寫一版初稿，再用下面第 4 階段的方式檢查。小篇幅的
東西（一封信、一段公告）不用走完整流程。

## 第 1 階段：蒐集背景

目標是補上「使用者知道、你不知道」的落差。先問最影響內容的幾件事，
一次問 3 到 5 個，不要一次丟一長串：

- **讀者是誰**？他們已經知道什麼、讀完要做什麼決定或動作？
- **這份文件要達成什麼**？（核准預算、對齊做法、留下紀錄……）
- **有沒有既定格式**或範本？（公司的簽呈格式、規格書範本）
- **現有的素材**：會議紀錄、舊文件、數據、相關的討論。請使用者上傳或
  貼上；有知識庫工具時，主動搜尋相關的規章與舊文件。
- **限制與敏感處**：時程、預算、不能寫進去的內容、需要誰審核。

讀完素材後，用幾句話複述你理解的重點與還不清楚的地方，請使用者更正。
資訊夠了再進下一階段；不要自己補數字、日期或人名。

## 第 2 階段：決定架構

1. 依文件類型與讀者提出大綱：每一節一行標題加一句「這節要回答什麼」。
   常見骨架（依需要取捨）：
   - **提案／簽呈**：摘要與請求事項 → 背景與問題 → 方案與比較 → 成本與
     效益 → 風險 → 時程 → 請求的決定
   - **規格書／技術設計**：目的與範圍 → 現況 → 需求 → 設計 → 替代方案與
     取捨 → 測試與上線 → 未決事項
   - **決策文件**：要決定什麼 → 選項 → 評估標準 → 建議與理由 → 影響
2. **重要的結論放最前面。** 忙碌的讀者可能只看第一段，摘要要能單獨成立。
3. 和使用者確認大綱，調整順序或增刪章節後再開始寫。

## 第 3 階段：逐節撰寫

- **一次處理一節**（或幾個短節）。先問這節還缺什麼資訊，再寫草稿。
- 每節寫完給使用者看，請他指出不對、太長、太短或語氣不對的地方，改到
  他滿意再往下。遇到同一類意見（例如「太官腔」），之後的章節一起套用。
- 寫作原則：
  - 先講結論，再講理由與細節。
  - 具體：用數字、日期、負責人，少用「大幅」「盡快」「相關單位」。
  - 一段一個重點；清單只用在真的是並列或步驟的內容。
  - 用讀者懂的詞，第一次出現的縮寫與術語要解釋。
  - 不確定的地方標成「【待確認：……】」，不要猜。
- 文件長的時候，在工作資料夾維護一份草稿檔（Markdown，或使用者要的
  Word 格式，有 docx skill 時照它的做法），每節改完就更新，最後再整份
  交付。

## 第 4 階段：讀者測試

全部寫完後，假裝自己是**第一次拿到這份文件、沒有參與討論**的目標讀者，
從頭讀一遍，並回報：

1. 用三句話摘要這份文件在說什麼、要讀者做什麼。摘要和作者的意圖不符，
   就是文件沒寫清楚。
2. 讀者最可能提出的 3 到 5 個問題，以及文件裡有沒有答案。
3. 讀不懂、前後矛盾、缺少依據或數字對不起來的地方。
4. 可以刪掉而不影響理解的段落。

把發現的問題和修改建議列給使用者，經他同意後修改。最後再檢查一次格式、
編號、日期與數字是否一致，交付成品並告訴使用者檔名。

## 交付

- 使用者要 Word、PowerPoint 或 PDF 時，交給對應的 skill（docx、pptx、pdf）
  產生檔案；沒有指定時，用 Markdown 寫在回覆或工作資料夾裡。
- 附上一段簡短說明：文件的重點、仍標著【待確認】的事項、建議誰先審。
