# Skill 建立器

用來建立新 skill，並反覆改進它的 skill。

skill 是一段「需要時才展開」的任務指示。agent 平常只看到每個 skill 的
名稱與一句 description，判斷用得到時才用 `load_skill` 載入完整內容。所以
skill 好不好，取決於兩件事：description 能不能讓 agent 在對的時機想到它，
以及內文能不能讓 agent 照著做出穩定的結果。

整體來說，建立 skill 的流程是：

- 決定這個 skill 要做什麼、大概怎麼做
- 寫出草稿
- 想幾個測試用的需求，實際照著 skill 做一遍
- 幫使用者從質與量兩方面評估結果
- 依使用者的評估（以及結果裡明顯的缺點）改寫 skill
- 重複，直到滿意為止
- 擴大測試集，在更大的規模上再試一次

你的工作是判斷使用者在流程的哪個階段，然後接手幫他往下走。例如使用者說
「我想做一個處理 X 的 skill」，你可以幫他釐清意思、寫草稿、寫測試案例、
決定怎麼評估、跑測試、再重複。

如果使用者已經有草稿，可以直接進入評估與改進的循環。

當然要保持彈性：如果使用者說「我不需要跑一堆評估，跟我一起調就好」，就
照他的方式做。

## 在這個環境

- **skill 放在哪裡：** 專案的 `skills/<名稱>/SKILL.md`（資料夾名稱與 `name`
  相同，小寫英文與連字號，例如 `monthly-report`）。用命令列時直接寫進專案
  資料夾。在網頁上，成員通常只能寫自己的工作資料夾：先寫在工作資料夾的
  `skills/<名稱>/`，完成後請管理者放到專案的 `skills/`。
- **先看現有的 skill**：用 `find_files` 找 `skills/*/SKILL.md`，避免重複，
  也沿用專案既有的寫法。內建的 skill 不能直接改：要調整時把它複製到專案的
  `skills/`（同名時以專案的為準）再修改。
- **frontmatter 格式**見 `template.md`（用 `read_skill_file` 讀取）。和
  Claude 的格式相比，Agent Harness 多了選用的 `tools`：載入 skill 後才開放
  的工具或 toolset。
- **開啟 skill**：在 agent 設定的 `skills` 欄位加上名稱（或不寫 `skills`
  欄位，讓 agent 使用專案的全部 skill）；網頁上也可以在每段對話的
  「＋ → Skills」選用。skill 有 `tools` 時，那些工具必須存在於專案裡。
- **沒有 subagent，也沒有 `claude` 命令列工具。** 官方流程裡平行跑測試、
  和沒有 skill 的版本比較、盲測比較、自動最佳化描述的步驟都不能用，改成下面
  「測試」與「描述最佳化」寫的做法。
- 附帶的 Python 腳本要用 `run_python` 在沙盒裡執行（腳本在
  `/opt/skills/skill-creator/`），沒有沙盒時跳過，改用文字呈現。

## 和使用者溝通

使用 skill 建立器的人，對程式術語的熟悉程度差異很大。所以要留意情境線索，
決定怎麼措辭。預設的情況下：

- 「評估」、「基準測試」勉強可以直接用
- 「JSON」、「assertion（斷言）」這類詞，要看到使用者明顯懂才不加解釋

不確定時可以簡短解釋術語。

## 建立 skill

### 釐清意圖

先了解使用者的意圖。目前的對話可能已經包含使用者想保存的工作流程（例如他說
「把這個做成 skill」）。這時先從對話紀錄找答案：用過的工具、步驟順序、
使用者做過的修正、觀察到的輸入與輸出格式。缺的部分請使用者補充，並在進入
下一步前請他確認。

1. 這個 skill 要讓 agent 做到什麼？
2. 什麼時候應該使用它？（使用者會怎麼說、在什麼情境）
3. 預期的產出格式是什麼？
4. 要不要建立測試案例來驗證 skill？產出能客觀驗證的 skill（檔案轉換、
   資料擷取、程式產生、固定的工作步驟）適合用測試案例；產出偏主觀的
   skill（寫作風格、藝術）通常不需要。依 skill 的類型建議預設做法，但讓
   使用者決定。

### 訪談與研究

主動問邊界情況、輸入輸出格式、範例檔案、成功標準與相依的工具。這部分
釐清之前，先不要寫測試需求。

有知識庫、網頁或其他工具能幫忙研究（查文件、找類似的 skill、查最佳做法）
時，先做功課，減輕使用者的負擔。

### 撰寫 SKILL.md

依訪談結果填寫這些部分：

- **name**：skill 的識別名稱
- **description**：什麼時候使用、做什麼。這是決定 skill 會不會被使用的
  主要依據，要同時寫出 skill 做什麼，以及具體什麼情境要用它。所有「什麼
  時候用」的資訊都寫在這裡，不要寫在內文。注意：目前模型傾向**少用**
  skill，在有用的時候沒有用。為了避免這個問題，description 寫得稍微
  「積極」一點。例如不要只寫「如何建立顯示內部資料的簡單儀表板。」，而是
  寫「如何建立顯示內部資料的簡單儀表板。使用者提到儀表板、資料視覺化、
  內部指標，或想顯示任何公司資料時都要使用，即使他沒有明說『儀表板』。」
  寫進使用者實際會說的字眼。
- **tools**（Agent Harness 選用）：載入後才開放的工具
- **compatibility**：需要的工具、相依套件（選用，很少需要）
- **其餘的內文**

### Skill 寫作指南

#### Skill 的結構

```
skill-name/
├── SKILL.md（必要）
│   ├── YAML frontmatter（name、description 必要）
│   └── Markdown 指示
└── 附帶資源（選用）
    ├── scripts/    - 處理固定、重複工作的可執行程式
    ├── references/ - 需要時載入上下文的文件
    └── assets/     - 產出會用到的檔案（範本、圖示、字型）
```

#### 漸進式揭露

skill 用三層的載入機制：

1. **中繼資料**（name + description）：一直在上下文裡（約 100 字）
2. **SKILL.md 內文**：skill 被使用時放進上下文（理想是 500 行以內）
3. **附帶資源**：需要時才讀（沒有上限，腳本不用讀進來就能執行）

這些字數只是大概，需要時可以寫長一點。

**重點模式：**

- SKILL.md 控制在 500 行以內；快超過時，多加一層結構，並清楚指出使用
  skill 的模型接下來該去哪裡找。
- 在 SKILL.md 清楚寫出參考檔案，以及什麼時候該讀（agent 用
  `read_skill_file` 讀取）。
- 大的參考檔（超過 300 行）加上目錄。

**依領域組織**：skill 支援多個領域或框架時，依變體分開：

```
cloud-deploy/
├── SKILL.md（工作流程 + 選擇）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

agent 只讀相關的參考檔。

#### 不出人意料的原則

不用多說：skill 不能包含惡意程式、攻擊程式碼，或任何可能危害系統安全的
內容。skill 的內容如果描述出來，不應該讓使用者對它的意圖感到意外。不要
配合建立誤導人的 skill，或用來未經授權存取、外洩資料或其他惡意行為的
skill。「扮演某某角色」這類是可以的。

#### 寫作模式

指示盡量用祈使句。

**定義產出格式**，可以這樣寫：

```markdown
## 報告結構
一律使用這個範本：
# [標題]
## 摘要
## 主要發現
## 建議
```

**範例模式**：加上範例很有用，可以這樣寫（範例裡有「輸入」「輸出」時可以
稍微變化）：

```markdown
## Commit 訊息格式
**範例 1：**
輸入：加入以 JWT token 進行的使用者驗證
輸出：feat(auth): implement JWT-based authentication
```

### 寫作風格

與其用一堆生硬的「必須」，不如向模型解釋**為什麼**重要。運用同理心，讓
skill 通用，不要過度侷限於特定範例。先寫草稿，再用新的眼光看一遍並改進。

另外，依我們的經驗：一步一件事、依執行順序排列；寫清楚判斷標準與例外
（例如「金額超過一萬元時先問使用者」）；只寫 agent 自己不知道的事（專案
慣例、內部規則、踩過的坑），通用常識不必重複。

### 測試案例

寫完 skill 草稿後，想 2 到 3 個真實的測試需求，也就是真正的使用者會說的
話。拿給使用者看（不一定要用這些字）：「我想試試這幾個測試案例，看起來
對嗎？還是要再加？」然後執行。

把測試案例存在 skill 資料夾的 `evals/evals.json`。先不要寫斷言，只寫需求；
斷言在下一步、執行測試時再擬。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "使用者的需求",
      "expected_output": "預期結果的描述",
      "files": []
    }
  ]
}
```

完整的 schema（包括之後要加的 `assertions` 欄位）見
`references/schemas.md`。

## 執行與評估測試案例

這個環境沒有 subagent，所以照官方在 Claude.ai 上的做法：

**執行測試案例**：一次一個。讀 skill 的 SKILL.md，照它的指示自己完成測試
需求。這比用獨立的 subagent 不嚴謹（skill 是你寫的、執行的也是你，你有
完整的上下文），但仍是有用的檢查，人工檢視可以彌補。跳過「沒有 skill 的
基準版本」，直接用 skill 完成需求。

產出放在 `<skill 名稱>-workspace/iteration-<N>/<測試名稱>/outputs/`（和 skill
資料夾並列；每一輪一個 `iteration-N`，每個測試案例一個資料夾，取能看出
在測什麼的名稱）。需要時再建資料夾，不用一開始全建好。

**擬斷言**：產出能客觀驗證的測試，擬幾個有清楚名稱、能客觀判斷的斷言，並
向使用者說明它們檢查什麼。能用程式檢查的斷言，寫程式檢查，不要用眼睛看：
程式比較快、可靠，而且每一輪都能重複用。主觀的 skill（寫作風格、設計品質）
用質性評估比較好，不要硬加斷言。評分的方法見 `agents/grader.md`（用
`read_skill_file` 讀取），結果存成 `grading.json`，`expectations` 陣列的
欄位要用 `text`、`passed`、`evidence`。

**檢視結果**：在對話裡直接呈現結果。每個測試案例列出需求與產出；產出是
使用者需要看的檔案（例如 .docx 或 .xlsx）時，存到工作資料夾並告訴他
檔名。直接問意見：「看起來怎麼樣？有什麼想改的？」

測試案例多、能用 `run_python` 時，也可以產生官方的檢視頁：
`python /opt/skills/skill-creator/eval-viewer/generate_review.py <workspace>/iteration-N --skill-name "<名稱>" --static <工作資料夾>/review.html`
（沙盒裡不能開瀏覽器或伺服器，一定要加 `--static`）。使用者下載後用瀏覽器
開啟，可以逐一看產出、留下意見，按「Submit All Reviews」會下載
`feedback.json`；請使用者把它上傳回來，再讀取意見。

**基準測試與盲測比較**：需要 subagent，跳過。

## 改進 skill

這是整個循環的核心。跑完測試、使用者看過結果後，依他的意見讓 skill 變得
更好。

### 怎麼思考改進

1. **從意見中歸納。** 我們要做的 skill 會被用上無數次，用在各種不同的需求
   上。你和使用者只在少數幾個例子上反覆修改，是因為這樣比較快：使用者對這些
   例子瞭若指掌，能快速判斷新的結果。但如果做出來的 skill 只對這些例子有用，
   它就沒有用。與其做過度擬合的細微修改，或加上壓迫性的「必須」，遇到頑固的
   問題時，試著換個比喻，或建議不同的工作模式。嘗試的成本不高，也許就會
   找到很好的做法。

2. **保持精簡。** 拿掉沒有發揮作用的內容。不只看最後的產出，也要回顧過程：
   如果 skill 讓模型花很多時間做沒有生產力的事，試著拿掉造成這種情況的部分，
   看看結果如何。

3. **解釋原因。** 努力解釋你要求模型做的每件事背後的**原因**。現在的 LLM
   很聰明，有良好的同理心，在好的環境下能超越死板的指示，真正把事情做好。
   即使使用者的意見很簡短或帶著挫折，也要試著真正理解工作，以及使用者
   為什麼這樣寫、實際寫了什麼，再把這份理解寫進指示裡。如果你發現自己在
   用全大寫寫「一律」或「絕不」，或用非常僵硬的結構，那是警訊；可以的話，
   改成說明理由，讓模型明白這件事為什麼重要。這是更人性、更有力、更有效的
   做法。

4. **找出測試案例間重複的工作。** 如果每個測試案例都各自寫了類似的輔助
   腳本，或用了同樣的多步驟做法（例如都寫了 `create_docx.py` 或
   `build_chart.py`），這是很強的訊號：skill 應該附帶這支腳本。寫一次、
   放在 `scripts/`，並告訴 skill 去用它。這樣之後每次使用都不用重新發明
   輪子。

這件事很重要，你的思考時間不是瓶頸；慢慢來，好好想清楚。建議先寫一版
修改草稿，再用新的眼光看一遍並改進。盡力站在使用者的角度，理解他想要、
需要什麼。

### 改進的循環

改進 skill 之後：

1. 把改進套用到 skill
2. 把所有測試案例重跑一次，放到新的 `iteration-<N+1>/`
3. 呈現結果（或產生新的檢視頁）
4. 等使用者看完並告訴你
5. 讀新的意見，再改進，重複

持續進行，直到：

- 使用者說他滿意了
- 意見都是空的（一切看起來都很好）
- 已經沒有明顯的進展

## 描述最佳化

SKILL.md frontmatter 裡的 description，是決定 agent 會不會使用 skill 的
主要機制。建立或改進 skill 後，主動提議調整 description，讓它在對的時機
被使用。

官方的自動最佳化（`scripts/run_loop.py`）要用 `claude -p` 反覆測試，這個
環境沒有，所以改成人工做法：

1. **產生觸發測試需求**：寫 20 個需求，混合應該使用與不應該使用這個 skill
   的情況：

   ```json
   [
     {"query": "使用者的需求", "should_trigger": true},
     {"query": "另一個需求", "should_trigger": false}
   ]
   ```

   需求要真實，是使用者真的會打的話。不要抽象的需求，要具體、有細節：檔案
   路徑、使用者工作或處境的背景、欄位名稱與數值、公司名稱、網址，一點點
   來龍去脈。有些可以是口語、有縮寫或錯字。長短混合，著重在邊界情況，而不是
   一看就知道答案的。

   不好：「整理這份資料」、「從 PDF 擷取文字」、「做一張圖表」

   好：「主管剛傳給我一個 xlsx（在我的下載資料夾，好像叫『Q4 業績 最終版
   v2.xlsx』），要我加一欄利潤率百分比。營收在 C 欄、成本應該在 D 欄」

   **應該使用**的需求（8 到 10 個）：考慮涵蓋面。同一個意圖的不同說法，
   有正式也有口語。包括使用者沒有明說 skill 或檔案類型、但顯然需要它的情況。
   加幾個少見的用法，以及這個 skill 和其他 skill 競爭但應該勝出的情況。

   **不應該使用**的需求（8 到 10 個）：最有價值的是「差一點」的需求：和
   skill 有共同的關鍵字或概念，但其實需要別的東西。想想相鄰的領域、字面
   比對會誤判的模糊說法，以及需求碰到 skill 做的事、但在那個情境用別的
   工具比較合適的情況。

   要避免的是：不應該使用的需求明顯無關。用「寫一個費氏數列函式」當 PDF
   skill 的反例太簡單了，測不出什麼。反例要真的有難度。

2. **和使用者一起檢視**這份清單（直接列在對話裡），請他修改。

3. **逐一判斷**：對每個需求，只看所有 skill 的名稱與 description（就像
   agent 實際看到的那樣），判斷會不會使用這個 skill，標出判斷錯的需求，
   再依這些錯誤改寫 description。注意：agent 只會在自己不容易處理的工作上
   查閱 skill，簡單、一步就能完成的需求（例如「讀這個檔案」）就算描述完全
   符合也可能不會使用，所以測試需求要有足夠的份量。

4. **套用結果**：更新 SKILL.md 的 description，給使用者看修改前後的差異。

## 驗證與打包（選用）

- `scripts/quick_validate.py <skill 資料夾>` 檢查 Claude 的 skill 格式。
  Agent Harness 的 `tools` 欄位不在 Claude 的格式裡，它會回報「Unexpected
  key」，這個可以忽略；其他問題要修正。
- 使用者想把 skill 帶到 Claude 使用時，可以用
  `cd /opt/skills/skill-creator && python -m scripts.package_skill <skill 資料夾> <輸出資料夾>`
  打包成 `.skill` 檔（會先驗證格式，有 `tools` 欄位時要先拿掉）。

## 修改現有的 skill

- **保留原本的名稱。** 資料夾名稱與 frontmatter 的 `name` 都不要改。
- 先用 `read_file` 讀完整的 SKILL.md，再用 `edit_file` 只改需要的地方，
  不要整份重寫。改 description 時特別小心，它決定 skill 會不會被使用。
- 改之前可以把原本的版本複製一份到 workspace，方便比較。

## 回報結果

列出建立或修改了哪些檔案，並提醒使用者：要在 agent 設定的 `skills` 欄位
加上這個名稱（或不寫 `skills` 欄位，讓 agent 使用全部 skill）；skill 有
`tools` 時，那些工具必須存在於專案裡；在網頁上寫在工作資料夾的 skill，
要請管理者放到專案的 `skills/` 才會生效。
